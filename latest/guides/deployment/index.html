Deployment¶

Use retail-setup deploy to provision, publish, update, or recover a demo workspace. Complete Getting started first if you have not configured the repository and rendered its notebooks.

This guide is for operators, developers, and support engineers. Business analysts can start with deployment outcome and troubleshooting, skipping the advanced authentication details.

See the plain-language glossary for terms such as Terraform, preflight, terminal success, Direct Lake, and DEGRADED.

The deployment framework specification defines exact command order and failure behavior.

Confirm the target

--recreate destroys the configured workspace and every item in it. The deploy polls Fabric until the workspace name is absent and fails before apply if deletion times out or pagination is incomplete. Use recreate only for a disposable demo workspace after confirming the tenant, environment, workspace name, and Terraform state.

Deployment outcome¶

Every deployment resolves deployment.profile from contracts/retail-demo.json. The manifest selects stable logical asset IDs, existing notebook groups, existing pipeline folders, and existing KQL scripts. It does not redefine physical items or schemas: deploy/config/deploy.yml, deploy/scripts/build_artifacts.py, and the source folders remain authoritative for those definitions.

The current deploy plan:

  1. resolves the exact profile inventory;
  2. runs local and live tenant/capacity preflight before Terraform destroy/apply, publication, or KQL;
  3. generates profile-aware Terraform and fabric-cicd inputs;
  4. initializes Terraform, saves and validates a plan, then applies that exact plan after confirmation unless Terraform is skipped;
  5. captures the selected Terraform-owned identifiers;
  6. stages and publishes infrastructure without Reporting;
  7. executes only the selected ordered KQL scripts and validates infrastructure;
  8. for gated profiles, waits for setup, then runs the six independent required ML producers concurrently and waits for their shared validator;
  9. stages and publishes Reporting only after required ML terminal success;
  10. runs selected optional/experimental ML through a single Spark lane while independent Reporting validation and API publication branches run through a bounded non-Spark worker pool;
  11. tells the Lakehouse SQL endpoint about newly created tables so Power BI and readiness queries can find them;
  12. for full-demo, runs the deployed ontology notebook to create or revalidate the target ontology and its derived graph;
  13. publishes both Data Agents and the complete task flow (14 tasks, 60 item references, 14 edges), then reads the graph back and compares every task, item binding, and edge;
  14. runs read-only readiness verification over the complete selected profile.

Each live run atomically updates deploy/.generated/<env>/deploy-run.json. This journal records target names, the manifest version/hash, profile support and expected counts/folders, core/optional/preview/manual boundaries, exact asset/group/pipeline/KQL inventory, required/optional classification, any failed step, its exit code, and the final SUCCEEDED, DEGRADED, or FAILED status. Artifact build steps link phase-specific artifact-inventory-<phase>.json evidence. Credential-like error text is redacted and raw subprocess output is not stored.

The final journal status is:

  • SUCCEEDED: every selected required and optional check passed.
  • DEGRADED: required capabilities passed, but at least one optional capability has failed, stale, or missing evidence. The required demo path is usable; inspect the linked report before presenting the affected optional feature.
  • FAILED: a required capability failed or could not provide evidence. Do not present the workspace as ready.

Native Operations Agent and Planning¶

The availability decision pack is separate from fabric-cicd publication. Its Operations Agent deploys by default with every Reporting profile (standard or full-demo, the default) after Reporting; core cannot select it. If Fabric rejects agent creation, the deploy step and readiness report a warning and the rest of the deployment continues. Native Planning stays excluded (include_plan: false) unless you explicitly include it.

Before publication, use a non-trial Fabric capacity, provide an Eventhouse or ontology (plus its KQL database when using Eventhouse), and ensure the creator has a Teams account. A Fabric administrator must enable Operations Agent, Copilot, and Azure OpenAI permissions. The API publisher uses a user identity with Contributor-or-higher workspace access and Item.ReadWrite.All; service principals and managed identities aren't supported for Operations Agent creation. If the capacity is outside the US/EU, enable the documented Azure OpenAI cross-geo processing/storage settings as well. The current tenant settings index has no separate Operations Agent creation toggle; its Operations Agent observability and insights settings are optional.

The deployment preflight checks the configured capacity and the Copilot/Azure OpenAI tenant settings it can inspect. It does not prove that a Teams account exists or that the Operations Agent preview is enabled for the creator's tenant/security group. The publisher creates the Agent stopped with its KQL source and instructions. The public definition API rejects FabricJobAction, so publication then uses the same OA workload endpoint as the Fabric UI to bind prepare-replenishment-case and requires exact source/action readback. It omits an empty playbook because Fabric rejects it with No rule definitions available; generate and review the playbook and Teams destination, then explicitly start only after review.

The default selection deploys only the Operations Agent and leaves the existing model's SSO binding untouched. It is equivalent to:

operations_planning:
  enabled: true
  include_plan: false

Set enabled: false only to skip the pack in a specific environment. This configuration works with the normal deployment and the targeted publisher. It does not require a Plan connection, Planning billing acknowledgement, or fixed credentials. Readiness requires the draft notebook and reports a missing Operations Agent as a warning, not a failure. It does not expect a Plan. Operators can review the Lakehouse draft-case table and existing report through SSO; this is not the native Planning product. Operations Agent remains stopped until reviewed and explicitly activated.

The publisher creates the supporting KQL tables and bound draft notebook before validating monitoring signals. Stale or invalid source evidence still blocks signal seeding and agent creation, but leaves those supporting assets published and records the failure in the current environment's report.

Native Planning does not support the current Direct Lake SSO path. Do not bypass organizational policy with an alternate identity or connection type. Only where fixed credentials are permitted, enable both components in deploy/config/environments/<env>.yml:

operations_planning:
  enabled: true
  include_plan: true
  plan_connection_id: <shared-Power-BI-Semantic-Model-connection-UUID>
  plan_billing_acknowledged: true
  recipient: <optional-Teams-user-principal-name>

Remove recipient if notifications will be configured later. Never put a password or access token in this block. For the connection, use Manage connections and gateways in Fabric to create a Cloud / Power BI Semantic Model connection, authenticated with OAuth2 or a properly provisioned service principal. The public connector type is PowerBIDatasets; its connection is identity-based, while the Plan definition separately binds retail_model. A personal, Analysis Services/XMLA, or Lakehouse SQL connection is not a substitute. WorkspaceIdentity is not supported on this Plan-to-model hop. Public connection creation does not expose an OAuth2 credential payload, so create/share that connection in the Fabric UI. The connection owner needs workspace Member/Admin and the required model access.

Separately, open retail_model Settings / Gateway and cloud connections, create/select a fixed-credential data-source connection, and apply it instead of the default Automatic/SSO binding. This model-to-OneLake hop is distinct from plan_connection_id. The publisher inspects both hops and never silently rebinds the existing model. See Microsoft's Planning connection setup.

Planning has a separate billing boundary

Creating, opening, or saving a Plan can start a 30-day billable Planning session. It cannot be manually ended; pausing or deleting capacity does not cancel that session. Set the acknowledgement only after accepting this cost. See Planning billing.

Once configured, retail-setup deploy --env <env> publishes the pack after Reporting. To add/update it in an already deployed workspace without rerunning historical generation, run from the repository root:

python -m deploy.scripts.deploy_operations_planning --environment retail-demo

--dry-run makes no service calls. --operations-only explicitly publishes only the Operations Agent and its supporting assets, without creating a Plan or requiring a Plan connection/billing acknowledgement. Set include_plan: false for a persistent operations-only deployment/readiness selection. A one-off --operations-only run does not satisfy a configuration that still requests both components.

If verified availability signals and the action notebook are already published but agent creation failed, retry only the stopped Agent without reingesting duplicate signal rows:

python -m deploy.scripts.deploy_operations_planning `
  --environment retail-demo `
  --agent-only

The publisher creates the item metadata, updates its stopped definition through the public API, then configures it through the delegated workload endpoint used by the UI. An HTTP 400 UnknownError from a public FabricJobAction update is distinct from tenant enablement and is not retried through that incompatible contract.

Disabling the pack stops its publication; it does not delete its items or stop an agent that an operator previously activated. Stop monitoring explicitly in Fabric before opting out. Readiness tolerates only the source-declared Operations tables left behind by an unselected pack, not arbitrary extra KQL objects, and never treats them as evidence of a running retail stream.

The model publication includes additive Next 7 Days forecast/bound measures; existing full-horizon measures remain unchanged. When including the Plan, publish the updated Reporting model before using the targeted command against an older deployment.

The pack publishes retail-availability-operations stopped, the separate prepare-replenishment-case notebook, and at most 100 current store/product signals. It binds the notebook as a human-approved Agent action through the UI-native OA workload endpoint. It publishes the native retail-replenishment Plan when requested. The standalone command also refreshes signals; it does not install a continuous forecast-to-Eventhouse feed. Source data older than seven days requires fresh historical inputs and a required-ML rerun before seeding; rerunning ML over unchanged old data does not advance its source time. The targeted publisher also uses capacity auto-resume. Plan prerequisites apply only when including the Plan; operations-only publication uses the configured operator login.

Inspect deploy/.generated/<env>/operations-planning-report.json for persisted item identities and remaining acceptance steps. In Fabric, review/generate the agent playbook, configure Teams notifications, and confirm human approval before explicitly starting monitoring. If selected, open the Plan to confirm its shared model connection and application database, then configure and accept any approval/writeback workflow in-product. Item publication is not proof those interactive capabilities have been accepted.

The notebook creates a durable DRAFT in the Lakehouse ops schema. It never places a purchase order or moves stock. The pack has no agent-to-Plan Optimize API, ERP adapter, or automatic Plan writeback bridge. The existing workspace task flow retains its supported artifact bindings; find the native items by their names in the workspace.

See the decision-experience boundary.

TMDL ontology and Fabric Apps approvals¶

Two optional steps also run by default. A failure in either degrades the run without stopping deployment.

  • publish-ontology-tmdl (full-demo) republishes RetailOntology_AutoGen in the new TMDL ontology format, with nine business rules, before the Data Agents are published. Fabric retires the old format on Jan 31, 2027. An old-format item is replaced only after a staged copy passes readback. Evidence: deploy/.generated/<env>/ontology-report.json.
  • deploy-fabric-app (standard and full-demo) deploys three Fabric Apps from app/fabric-app with the Rayfin CLI: retail-merchandising, retail-promotions, and retail-approvals. Each is staged under deploy/.generated/<env>/fabric-apps/<app>/ with its own Rayfin identity, and a new app is deployed a second time in the same run once its sign-in origin is known. The apps stand alone and do not link to each other. It needs Node.js 20+, the Fabric Apps (preview) tenant setting, and a capacity region that supports Fabric Apps. The first run can open a browser for the Rayfin sign-in. To deploy only the apps, run python -m deploy.scripts.deploy_fabric_app --environment <env>. Evidence: deploy/.generated/<env>/fabric-app-report.json.

Store, Warehouse, and Truck twins¶

The connected twins are a separate, read-only Power BI report named retail-twins. They use the existing semantic model's Automatic/SSO binding and are independent of native Planning and Operations Agent.

They deploy by default with every Reporting profile (standard or full-demo). To skip them in one environment, set this in deploy/config/environments/<env>.yml:

twins:
  enabled: false

The normal deployment publishes the report after Reporting. For an existing workspace, use the targeted publisher without regenerating historical data:

python -m deploy.scripts.deploy_twins --environment retail-demo

--dry-run makes no service calls. The targeted publisher selects a connected route and cargo cohort of limited size, adds only the required twin model objects, preserves SSO, and publishes the report. It does not change credentials, create a native Digital Twin Builder item, start an agent, or execute orders. Capacity auto-resume uses the existing deployment mechanism.

The pilot contains one DC, two trucks, up to five connected stores, and up to twenty cargo SKUs. Selection follows recorded relationships rather than assuming that the first numbered entities are connected. Historical source time, signed stock, and the separate +60 minute delay what-if are visible. Warehouse on-hand is not confirmed available supply; truck state is not GPS.

Open the report link recorded in deploy/.generated/<env>/twins-report.json using your Fabric/Power BI login. That file also retains source/cohort evidence, model changes and their backup, and the publication outcome. The publisher refreshes Direct Lake framing without changing SSO. Status reads retry transient connection errors against the exact accepted refresh request; they never start a duplicate refresh. Use the network's entity fields to drill through to Store, Warehouse or Truck views; the page tabs remain available. Inspect page rendering and navigation before presenting the demo. See the connected-twin specification.

Profiles¶

full-demo is the default for every entry point: the guided wrappers, scripts/setup.py, and direct retail-setup commands. It deploys every publishable feature, including live-checked preview items, the connected twins report, and the Operations Agent. standard and core are reduced inventories you must select explicitly with --profile. The workspace and profile inventory is the single canonical guide for exact asset IDs, groups, pipelines, KQL scripts, staged counts, folders, and support status.

All profiles exclude the destructive reset group. Pipeline selection is explicit; a notebook reference does not implicitly select a pipeline. No profile enables a schedule or starts the long-running stream.

Runtime, capacity, cost, preview, and manual boundaries¶

The dry run prints the manifest's runtime, capacity, cost, preview, and manual boundaries for the resolved profile. A live full-demo run reads Fabric tenant settings and capacity metadata before mutation. Reporting remains absent unless the current required ML pipeline run, including the runtime contract validator, finishes successfully.

The deploy runner uses an explicit dependency graph rather than treating the plan as one serial list. Spark-heavy deployment steps default to one concurrent lane, while up to four independent non-Spark/API steps can overlap. Required failures block only their descendants; optional failures degrade the run without cancelling independent siblings. Task flow, folder reconciliation, and readiness remain final joins and start only after every selected branch is terminal.

Prerequisites¶

Local tools¶

  • Git
  • Python 3.11 or later
  • Terraform >= 1.8, < 2.0
  • retail-setup
  • azure-identity
  • azure-kusto-data
  • fabric-cicd
  • pyodbc
  • the locked deploy dependency set, which includes the bundled mssql-python SQL driver on Windows and Linux; an installed Microsoft ODBC Driver 17 or 18 is used when available and remains required on macOS
  • Azure CLI for the default auth mode, or Azure PowerShell for the lower-level alternative

Install the Python dependencies manually when you are not using the guided bootstrap:

python -m pip install --require-hashes -r .\utility\requirements-deploy.txt
python -m pip install --no-deps -e .\utility

Fabric target¶

The operator must be able to:

  • use the selected tenant and active Fabric capacity;
  • create or update the target workspace and Fabric items;
  • create or publish every item type selected by the chosen profile;
  • apply KQL schema when the profile includes Eventhouse;
  • perform the profile's documented manual steps.

Use a dedicated workspace and review workspace and item roles before sharing access. Keep generated customer-like fields within the demo's access rules.

Resume a paused Azure Fabric capacity¶

Deployment automatically resumes a paused or suspended Azure F-SKU capacity using its configured name in deploy/config/environments/<env>.yml:

workspace:
  capacity_name: myfabriccapacity

The preflight discovers the matching Azure resource through ARM. If subscription_id is configured, only that subscription is searched; otherwise it searches accessible subscriptions owned by the configured tenant. Subscription and capacity pagination must complete, and the name must identify exactly one Azure Fabric capacity. Missing, duplicate, or incomplete results fail before any resume request.

Set workspace.capacity_resource_id to select an exact resource without name discovery. Copy Resource ID from Azure portal properties; it has the form /subscriptions/<subscription-id>/resourceGroups/<resource-group>/providers/Microsoft.Fabric/capacities/myfabriccapacity. This is not the Fabric GUID in capacity_id. The Azure resource name must agree with the configured Fabric capacity, and its subscription must match subscription_id when that value is set.

Active capacity is left unchanged and does not require Azure management permissions. Otherwise, the operator needs Azure RBAC permission to discover the relevant subscriptions/capacities, read and resume the capacity, and track its operation; Fabric workspace roles alone are insufficient. An explicit resource ID avoids subscription discovery. The same configured tenant and authentication mode are used with separate Fabric and Azure management tokens.

Resuming restarts capacity billing, even if a later deployment check fails. The preflight submits at most one resume request per attempt, waits for Azure and Fabric to report Active (up to ten minutes by default), and stops on permission errors, failed operations, unsupported states, or timeout. It does not scale, create, reassign, or automatically pause capacity. Throttled GET requests honor Retry-After within the same deadline; resume POSTs are not blindly retried. Inactive trial and Premium capacities must be resumed manually.

The live preflight is repeated on deploy --resume because capacity may have been paused between attempts. Dry runs and read-only readiness verification do not resume capacity. To run only this preparation step:

python -m deploy.scripts.live_profile_preflight --environment <env> --resume-capacity

Set --capacity-timeout-seconds on that command to change its wait limit. See Microsoft's capacity pause/resume guidance for permissions and billing details.

Authentication¶

Azure CLI¶

Azure CLI is the default and the only mode the guided bootstrap installs and checks automatically.

In an interactive terminal, both the guided setup and retail-setup deploy sign in to the configured tenant before deploying (az login --tenant, or Connect-AzAccount for auth.mode: azure_powershell). If the Windows account broker fails to store keys, sign-in is retried once in the browser. Pass --skip-login to reuse your current sign-in. Non-interactive runs, such as CI, don't sign in; they only check that the active tenant matches. To sign in manually:

az login --tenant 00000000-0000-0000-0000-000000000000
az account show --query tenantId -o tsv

Set:

auth:
  mode: azure_cli

retail-setup deploy rejects a configured tenant that differs from the active Azure CLI tenant.

Windows sign-in key-storage failures¶

An az login failure containing incorrect storage parent or error 2150171662 comes from Windows account-broker key storage, before Fabric deployment. The guided bootstrap retries this specific failure once using browser sign-in. It retains the same tenant and passes AZURE_CORE_ENABLE_BROKER_ON_WINDOWS=false only to the retry and the subsequent deployment process. It does not run az logout, clear account caches, change persisted CLI configuration, or modify the caller's environment.

Rerun the original setup command and complete the browser sign-in. Cancellations, Conditional Access denials, and unrelated failures are not retried; an unsuccessful retry stops deployment.

To continue an already configured deployment manually without rerunning setup:

$previousBroker = $env:AZURE_CORE_ENABLE_BROKER_ON_WINDOWS
try {
    $env:AZURE_CORE_ENABLE_BROKER_ON_WINDOWS = "false"
    az login --tenant 00000000-0000-0000-0000-000000000000
    if ($LASTEXITCODE -ne 0) { throw "Azure sign-in failed; deployment not started." }
    retail-setup deploy --env <env>
} finally {
    $env:AZURE_CORE_ENABLE_BROKER_ON_WINDOWS = $previousBroker
}

Replace the tenant and environment placeholders with the configured target. If browser sign-in is denied by organizational policy, ask the tenant/device administrator to resolve the broker or device-registration problem rather than weakening that policy. See Microsoft's Windows broker and browser sign-in guidance and configuration precedence.

PowerShell launcher fails on a repeat run¶

The expression after '&' ... was not valid can occur when an earlier Conda shell hook left an alias whose executable environment variable was subsequently restored or removed. Older launchers also mistook the alias's module Source (Conda) for a native executable path.

The launcher now resolves the actual Conda executable and activates through its native command, without importing persistent aliases or prompt hooks. Rerun .\scripts\setup.ps1 with the original arguments in the same window. This launcher repair does not sign in to Azure or deploy resources by itself; those remain later setup steps.

Azure PowerShell¶

Most users do not need this section

Use Azure CLI unless your organization specifically requires Azure PowerShell or an automated service identity. Azure PowerShell does not provide credentials to the Fabric Terraform provider, so this path needs additional identity configuration.

For a manually prepared workstation:

Connect-AzAccount -Tenant 00000000-0000-0000-0000-000000000000

Set:

auth:
  mode: azure_powershell

The deploy REST and KQL helpers use AzurePowerShellCredential with the configured tenant. The Fabric Terraform provider cannot consume an Azure PowerShell session. Therefore this mode supports either:

  • Python-only publication with --skip-terraform and previously captured, validated outputs; or
  • normal Terraform with exactly one provider-supported service-principal secret/certificate, OpenID Connect (OIDC) federated identity, or managed-identity credential configured through the provider's FABRIC_* or ARM_* environment variables.

Without one of these credential setups, apply and destroy fail before any command runs. Terraform always receives the configured tenant_id; Azure CLI use is explicitly disabled in Azure PowerShell mode, so an unrelated CLI login is never used silently. A conflicting FABRIC_TENANT_ID or ARM_TENANT_ID also fails before mutation. The guided scripts/setup.* prerequisite check still expects Azure CLI, so invoke retail-setup directly for this advanced flow.

Configure an environment¶

The workspace name defines the environment. configure normalizes the name to lowercase hyphenated text and omits a leading retail-demo- prefix. For example, workspace retail-demo-alice uses environment alice. Each workspace gets its own ignored target overlay, generated inputs, Terraform data directory, state, outputs, and run journal.

Run:

retail-setup configure --workspace-name retail-demo-alice
retail-setup render --env alice

configure prints the derived environment key. Configure another workspace to create another local environment without replacing the first.

Valid profiles are core, standard, and full-demo. Omitting --profile prompts with full-demo as the default. The selected value is stored in the workspace environment overlay as deployment.profile.

Configuration files:

Path Purpose Tracked
deploy/config/deploy.yml Shared deployment defaults Yes
deploy/config/environments/<env>.yml Workspace-specific target overlay No
utility/config/environments/<env>.yaml Environment-specific generation scale and seed No
utility/out/<env>/ Rendered workspace-specific notebooks and render manifest No

Legacy utility/config.yaml is a read fallback only when the environment's generation file is absent. Configure writes the new environment-specific path.

Keep the Eventhouse and KQL database display names aligned. The Eventhouse creates one default KQL database with the Eventhouse display name; provisioning a separately named database is not a supported topology.

Starter pool or custom pool¶

core and standard use the workspace starter pool. Only full-demo selects the custom pool. Live preflight resolves the target capacity's current F<n> or FTL<n> SKU and derives the pool before Terraform configuration is generated. The supported calculation uses base capacity only:

  • Spark base capacity is 2 vCores per capacity unit (CU).
  • The deploy reserves 25% headroom: usable_vcores = floor(CU * 2 * 0.75).
  • The required-ML pipeline's root notebook producer count is authoritative (currently six concurrent sessions).
  • Medium nodes use 8 vCores. Each session receives floor(usable_vcores / (producer_count * 8)) nodes, clamped to 2–16.
  • The minimum is min(2, max_nodes). Preflight fails if every producer cannot receive at least two Medium nodes (one driver and one executor).

This yields 2 nodes per session on F64, 4 on F128, 8 on F256, and the 16-node cap on F512 and larger. The calculation does not use or claim burst capacity. Live preflight writes bounded, non-secret evidence to deploy/.generated/<env>/capacity-sizing.json; custom-pool config generation requires fresh evidence for the configured environment and capacity. Starter pool profiles neither create nor consume this file. Legacy --use-custom-spark-pool and spark.use_custom_pool overrides fail clearly; select the profile instead.

On resume, live sizing is observed again. Before Terraform apply, a sizing change forces config regeneration and a new Terraform plan. After Terraform apply, a sizing change fails the resumed run and requires a new deployment plan instead of silently reusing the applied pool.

Preview the plan¶

retail-setup deploy --env alice --dry-run

The preview prints the resolved inventory, profile blockers, ordered commands, and confirmation gates. It validates the existing environment configuration and authentication boundary but does not execute subprocesses or:

  • contact identity endpoints or validate live permissions;
  • contact Fabric;
  • validate capacity state;
  • prove live generated IDs unless --skip-terraform is selected;
  • run Terraform plan as a separate command.

With --skip-terraform, dry-run validates the existing captured outputs just like a live run. Malformed or invalid existing YAML always fails; the default core fallback applies only when a legacy environment overlay is genuinely absent. On an actual deployment, the CLI saves and validates the Terraform plan before apply confirmation. Review it with terraform show deploy/.generated/<env>/terraform.tfplan before accepting. The current guard saves the plan output without displaying it. Apply consumes that exact saved plan. The plan guard blocks implicit workspace, Lakehouse, or Eventhouse deletion/replacement, including with --yes; use the explicit --recreate workflow for intentional destruction.

Preflight¶

Preflight checks the deployment before it changes resources. Local checks cover manifest source paths, committed notebook inputs, selected pipelines, KQL scripts, Power BI, agents, and task flow. They also check custom-pool configuration, prior Terraform state, captured profile outputs, and blockers.

A second, read-only live check verifies the capacity's identity, active state, size, region, and ability to host the requested Spark workers. For full-demo, it also reads the Fabric admin tenant-settings API to verify the required Ontology and Data Agent switches. After Terraform (or immediately when --skip-terraform is selected), target access validation requires captured workspace IDs to match managed resource IDs in state and a live workspace with the configured name that the operator can read.

The orchestrator's source-only check runs before rendering. If rendered validation is explicitly requested, it reads utility/out/<env>/; stale notebooks from another environment are not valid input evidence.

If preflight passes, deployment continues. If a required tenant switch is disabled, interactive deployment prints the exact Admin Portal setting and offers to recheck after an administrator changes it. Fabric documents tenant-setting inspection but no write API, so setup never silently changes tenant policy. Noninteractive deployment and invalid or inaccessible capacity fail before changing resources, with instructions for correcting the problem.

If environment-local Terraform state exists, deployment rejects missing or stale captured outputs and missing state profile evidence. This also applies to state with no managed instances. A profile downgrade that would delete an Eventhouse or custom Spark pool is rejected unless the operator explicitly selects --recreate.

Run a normal deployment¶

Interactive:

retail-setup deploy --env alice

Pre-confirm the Terraform apply gate:

retail-setup deploy --env alice --yes

Without --yes, an existing workspace detected by display name produces a choice:

  • keep it and update in place; or
  • reset it and follow the recreate path.

With --yes, the CLI does not perform that interactive existing-workspace check. It still runs mandatory setup and required ML gates for profiles that publish Reporting.

Understand generated files¶

Deployment writes or refreshes:

Path Content Git status
deploy/.generated/<env>/terraform.tfvars Terraform input generated from merged YAML Ignored
deploy/.generated/<env>/terraform.tfstate Environment-local Terraform state Ignored
deploy/.generated/<env>/terraform.tfplan Saved and guarded plan consumed by apply Ignored
deploy/.generated/<env>/.terraform/ Environment-local Terraform data directory Ignored
deploy/.generated/<env>/fabric-cicd/config.yml fabric-cicd environment and item scope Ignored
deploy/.generated/<env>/fabric-cicd/parameter.yml Workspace, item, OneLake, KQL, and agent rewrites Ignored
deploy/.generated/<env>/terraform-output.json Captured live Fabric item identifiers Ignored
deploy/.generated/<env>/database.kql Combined ordered KQL script Ignored
deploy/.generated/<env>/workspace/ Staged Fabric item folders, including post-ontology Ignored

Terraform operations for different environments use different backend and data paths. Generation configuration, rendered notebooks, and staged publication also use environment-local paths. Do not run concurrent deploys for the same environment or assume different environment keys lock a shared Fabric target. Never commit local target overlays, credentials, tokens, or generated bindings.

If an older checkout left state at deploy/terraform/terraform.tfstate, deploy stops before Terraform. Verify which workspace owns that state, then move it to deploy/.generated/<env>/terraform.tfstate. Never copy one legacy state into multiple environments.

Existing workspaces¶

For a workspace that Terraform should resolve rather than create, set workspace.existing_id in deployment configuration and run the normal Terraform path. This resolves the workspace only; it does not automatically discover or import pre-existing Lakehouse, Eventhouse, role-assignment, or Spark resources into Terraform state. Avoid name collisions and import or reconcile existing child resources deliberately before apply.

Use --skip-terraform only when all required resources already exist and deploy/.generated/<env>/terraform-output.json contains correct identifiers from an earlier deployment:

retail-setup deploy --env alice --skip-terraform

Before publication, the command verifies the captured environment, workspace and resource names, required Fabric IDs, and absence of placeholder IDs. A full-demo capture must also include the custom Spark pool ID. A first-time or wrong-workspace --skip-terraform run fails before mutation.

--skip-terraform cannot be combined with --recreate.

Recreate a disposable workspace¶

Preview:

retail-setup deploy --env alice --recreate --dry-run

Execute:

retail-setup deploy --env alice --recreate

The current sequence is profile preflight, configuration generation, Terraform initialization, Terraform destroy, bounded polling until the workspace name is absent, saved-plan validation and apply, and normal publication. Preflight therefore cannot destroy the workspace on failure. Preserve run evidence before retrying if Fabric does not release the workspace within the documented timeout.

Do not use 99-reset-lakehouse as part of normal deployment. It is a manual, destructive data reset asset.

Resume an interrupted deployment¶

retail-setup deploy --env alice --resume

Resume requires an incomplete deploy-run.json whose environment, targets, profile, manifest, ordered plan, and source/config fingerprint still match. Only the contiguous SUCCEEDED prefix is reused. A changed working tree or target requires a newly reviewed run, not journal edits to force compatibility. Completed runs cannot be resumed; --resume cannot be combined with --dry-run or --recreate.

Every orchestrated setup, required-ML, optional-ML, and experimental-ML step writes bounded correlation evidence under deploy/.generated/<env>/pipeline-evidence/. The file records the exact workspace, pipeline item ID, job ID, Fabric Location, submission time, observed status, and start/end timestamps. It is written immediately after Fabric accepts the POST, before status polling begins.

When a compatible journal contains a RUNNING pipeline step and that exact evidence file is present, --resume reattaches to the recorded Location. It never POSTs a replacement automatically. A completed run is adopted, an active run is awaited, and a failed/cancelled run remains failed. Missing, mismatched, duplicate, or source-incompatible evidence fails closed.

The runner separates the Fabric execution budget from local monitor availability. --monitor-timeout-seconds may end the local wait while the remote run remains active; the journal stays RUNNING and is resumable. The runner does not cancel the Fabric job. Resume with the same compatible sources to reattach.

If the local wait for the required ML pipeline fails but Fabric later records that exact run as successful, adopt it while resuming instead of launching the pipeline again:

retail-setup deploy --env alice --resume `
  --adopt-pipeline-run ml-required=<job-id>

This recovery verifies the exact completed run against the configured workspace and pipeline, checks that it started after the journaled setup run, and records its job ID in the new deployment journal. It continues with Reporting and later steps without repeating setup or required ML. The explicit adoption permits the source fingerprint to differ (for example, when the polling code was fixed after the deployment started); the environment, targets, profile, manifest, and ordered plan must still match. For a recreate deployment, both workspace destruction and the deletion wait must already have succeeded. This option only adopts the required-ML gate; it does not adopt setup or post-Reporting pipeline runs.

Pending Terraform apply regenerates and checks its saved plan. Pending item publication rebuilds its staging first, including Reporting and post-ontology phases. An unfinished destructive recreate phase requires explicit review and restart. Resume does not convert old local evidence into fresh Fabric proof. Prior recreate identity is retained only after all steps through the workspace-deletion wait succeeded; it is not permission to replay an unfinished destroy automatically.

The compatibility fingerprint includes sources, configuration, dictionaries, and ordered commands. Old journals without the required compatibility fields are not resumable. A different new/resumed run first archives the prior journal atomically at deploy/.generated/<env>/run-history/<hashed-run-id>.json, then replaces deploy-run.json; preserve both for diagnosis.

For phased Reporting profiles, leave deployment.unpublish_skip enabled. Setting it to false is rejected because unpublishing a partial stage could delete healthy Reporting items.

Post-deploy work¶

Demo folder organization¶

Items are organized by object type, not by deployment phase: all notebooks are in Notebooks, all pipelines in Pipelines, reports in Reports, semantic models in Semantic Models, and experiments in ML Experiments. Native add-ons use their own type folders, including Fabric Apps and Ontologies. Service-managed children stay with their parent as required by Fabric.

Normal deployment and standalone publishers preserve this layout. To reorganize an existing demo without rerunning data generation or publication:

python -m deploy.scripts.workspace_folders --environment retail-demo

The command preserves item IDs and removes only empty obsolete lifecycle folders. Its live readback is saved to workspace-folder-report.json.

Understand local validation¶

deploy.scripts.validate_deployment checks generated files, YAML, staging, and placeholder rewrites. It does not query the live workspace. A successful deploy still requires live item, binding, KQL, run, and data checks.

Generate data¶

For core, run setup notebooks 01 through 11 in order. core intentionally has no automatic pipeline run.

For standard and full-demo, the deploy command already waits for setup-pipeline and ml-required, publishes Reporting only after both succeed, and waits for selected post-Reporting ML pipelines. --yes does not skip these gates. No profile starts the long-running stream or enables an automatic schedule; the committed daily-maintenance schedule is disabled.

To retry one pipeline deliberately, run:

python -m deploy.scripts.run_pipeline `
  --environment alice `
  --pipeline setup-pipeline `
  --auth-mode azure_cli `
  --tenant-id <tenant-id> `
  --wait

--wait polls the exact submitted run to a bounded terminal state. Omit it only for an intentional asynchronous manual trigger. Use --evidence-output to select the durable JSON path. Use --reattach-location or --reattach-run-id to monitor an existing exact run without POSTing.

Pipeline submission is attempted once. If the POST response is lost, the runner lists runs for that exact workspace and pipeline and adopts only one known-state run in the bounded request window. Zero or multiple candidates fail closed; the runner does not retry the POST.

If a deployment stopped but every selected setup/ML pipeline was later recovered manually, adopt the exact successful Fabric job IDs instead of rerunning hours of Spark work:

  1. Open the Fabric Monitoring hub.
  2. Open each pipeline's run history.
  3. Copy the job ID from the successful run you want to adopt.
  4. Supply every pipeline selected by the stored profile.
Profile Required run IDs
core None; setup notebooks are run manually.
standard setup-pipeline and ml-required
full-demo setup-pipeline, ml-required, ml-optional, and ml-experimental

The example below is for full-demo. For standard, omit the ml-optional and ml-experimental lines.

python -m deploy.scripts.adopt_pipeline_runs `
  --environment alice `
  --run setup-pipeline=<job-id> `
  --run ml-required=<job-id> `
  --run ml-optional=<job-id> `
  --run ml-experimental=<job-id>

Supply every pipeline selected by the profile. Recovery validates the captured workspace against the live configured target, confirms that setup finished before required ML and required ML finished before optional ML, and accepts only explicitly named, completed runs from the last seven days. It then writes a current deploy-run.json, runs readiness, and finalizes the journal only after that verification result is known.

Synchronize the Lakehouse SQL endpoint¶

Reporting profiles do this automatically after setup and machine learning. The step tells Fabric's SQL endpoint that newly created Lakehouse tables exist, which allows Power BI and readiness queries to discover them. The step is optional because required-table availability is checked again by fail-closed readiness.

Run it manually when tables exist in the Lakehouse but Power BI or SQL queries cannot see them:

python -m deploy.scripts.refresh_sql_endpoint `
  --environment alice

The command waits for Fabric's metadata operation to finish and reports any table that did not synchronize.

The same artifact build also sets the deployed report's saved date filters to the month containing the configured history end_date. To change that default, update the history configuration, rerun retail-setup render, and deploy again.

Recover the ontology and task flow¶

Normal full-demo deployment completes this phase automatically. It runs the deployed 30-create-ontology notebook to create or revalidate RetailOntology_AutoGen, waits for the item to appear, publishes both Data Agents, and deploys the source-controlled task flow. The task-flow write is read back and compared with all 14 tasks, 60 selected item references, and 14 edges before the command reports success.

Use this recovery command when the final phase was interrupted or an operator removed one of its items. It is safe to repeat:

retail-setup post-ontology --env alice

The command reuses the same completion path. A Data Agent is a conversational Fabric experience that answers questions from an approved data source; the task flow is the workspace navigation map. Missing selected references, ambiguous task-flow records, or a graph that does not persist exactly all fail closed.

Validate live readiness¶

For standard, deployment runs the live verifier after the normal exact-run setup and ML gates. full-demo runs the complete verifier after ontology, Data Agent, and task-flow publication. Verification is read-only and never adds another pipeline run. A required failure or unknown result fails deployment; an optional failure or unknown result records DEGRADED in deploy-run.json. The journal links:

deploy/.generated/<env>/readiness-report.json

For core, run setup notebooks 01-11 manually, then run:

retail-setup verify --env <env>

You can rerun the read-only command for any profile. Add --run-pipeline only to explicitly start and wait for the profile-required post-publish pipeline:

retail-setup verify --env <env> --run-pipeline

The flag is invalid for core. It does not start streaming or other pipelines. See the operations readiness checklist for prerequisites, exit codes, taxonomy, freshness windows, and report contents. Offline validate_deployment.py behavior is unchanged and does not substitute for this live check.

If the optional stream has never been started, three streaming checks are expected to be UNKNOWN: Silver watermarks, Eventhouse ingestion, and checkpoint identity. Required capabilities can still pass, so the overall result is DEGRADED, not FAILED.

Update an existing deployment¶

For normal source or configuration changes:

  1. Pull or check out the intended revision.
  2. Rerun retail-setup configure when target or generation values changed.
  3. Rerun retail-setup render.
  4. Inspect retail-setup deploy --env <env> --dry-run.
  5. Run the normal deploy without recreate.
  6. Rerun only the data or optional workloads affected by the change.
  7. Validate live bindings and freshness.

Environment-local Terraform paths keep each workspace's local state separate. Preserve each environment's ignored .generated/<env>/ directory when its state and output evidence must survive cleanup.

Current limitations¶

IMP-* identifiers are named improvement items in the technical backlogs. Open a linked item to see its exact remaining acceptance criteria.

  • The generator, notebook packaging, batch ML, ancillary assets, Power BI, and readiness consistency changes still need a fresh combined validation run, including remote checks.
  • Live alternate-authentication and renamed-target smoke verification: IMP-001
  • Separate live core and standard profile proof keeps IMP-012 open.
  • Recent optional streaming freshness evidence: IMP-013

Local staging success, a task-flow node, a pipeline trigger, or a checked-in optional asset does not prove the live deployment is usable.
